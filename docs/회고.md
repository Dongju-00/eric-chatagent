## 배포에서 겪은 문제들

가장 많이 배운 구간이었습니다. 대부분의 시간을 "왜 로컬에서는 되는데 서버에서는 안 되지?"를 푸는 데 썼습니다.

### 1. 모델 파일이 이미지에 없던 문제

로컬에서 빌드한 이미지는 정상 동작했는데, GitHub Actions로 빌드한 이미지는 계속 토크나이저를 못 찾았습니다.

```
[Mac 로컬 빌드]
Mac 디스크 → COPY . . → 이미지
              ↑ .dockerignore가 거름
→ 모델 파일이 Mac 디스크에 있으니 이미지에 들어감 ✅

[GitHub Actions 빌드]
git 저장소 → checkout → VM 디스크 → COPY . . → 이미지
              ↑ .gitignore가 거름 (또는 애초에 커밋 안 됨)
→ 모델 파일이 git에 없으니 VM 디스크에도 없음 → COPY할 대상 자체가 없음 ❌
```

`.dockerignore`에서 모델을 제외하지 않았으니 당연히 들어갈 거라고 생각했는데, Actions VM 디스크에는 애초에 모델이 없었습니다. Actions에서 Docker을 로드한다고 해도 Git에 들어있는 것을 기반으로 한다는 것을 이 때 이해했습니다.

**해결**: 모델을 Hugging Face Hub에 올리고 Dockerfile 빌드 단계에서 내려받도록 변경했습니다. 결과적으로 역할 분담이 깔끔해졌습니다.

```
git       → 코드
HF Hub    → 모델 가중치
Docker Hub→ 완성된 이미지
Secrets   → 배포용 비밀값
서버 .env → 실행용 비밀값
```

### 2. compose의 `build: .`

Mac에서 새 이미지를 push했는데 EC2에서 `docker compose pull`을 해도 계속 옛 이미지의 에러가 났습니다.

원인은 compose 파일의 `build: .`였습니다. 이 설정이 있으면 compose가 해당 서비스를 "직접 빌드해야 하는 대상"으로 취급해서, pull을 건너뛰거나 로컬에 있는 옛 이미지를 계속 재사용합니다. 그런데 EC2에는 Dockerfile도 소스코드도 없으니 빌드는 애초에 불가능한 지시였습니다.

**배운 것**: 개발용 compose와 배포용 compose는 역할이 다릅니다. 배포 서버의 compose는 `image:`만 있어야 하고, 빌드는 CI가 담당합니다.

### 3. OOM (`Exited 137`)

비용을 줄이려고 인스턴스를 medium(4GB)에서 small(2GB)로 내렸더니 컨테이너가 시작 직후 죽었습니다. 파이썬 에러가 아니라 커널이 프로세스를 강제 종료한 것(SIGKILL)이었습니다.

메모리를 쓰던 것들을 정리해보니:

- KoreanGPT 체크포인트 3개를 **시작 시 한꺼번에 로드**
- PyTorch가 **CUDA 빌드**였음 — GPU도 없는 서버에서 nvidia 라이브러리만 2GB 이상
- ChromaDB + 임베더 초기화
- FastAPI / uvicorn

특히 두 번째가 컸습니다. GPU가 없는 환경에서 CUDA 빌드를 쓰는 건 **얻는 것 없이 무거운 짐을 지고 있던 상태**였습니다. 이미지가 8.6GB까지 부풀었던 것도, 배포마다 빌드·push·pull이 오래 걸렸던 것도 같은 원인이었습니다.

**대응**: `pyproject.toml`에서 torch를 CPU 빌드로 고정했습니다.

이 경험에서 **EC2 서버를 역할별로 나누자**는 결론에 도달했습니다. 지금은 웹 서버와 모델이 한 프로세스에 있어서 모델이 메모리를 터뜨리면 웹까지 같이 죽습니다. 분리하면 모델 쪽만 죽고 웹은 안내 응답을 반환할 수 있습니다.

### 4. 반복해서 겪은 것들

같은 종류의 실수를 여러 번 반복했고, 그 안에 패턴이 있었습니다.

| 증상 | 원인 |
| --- | --- |
| `tag does not exist` | 빌드 이름과 push 이름 불일치 |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | 인스턴스 재생성으로 IP 재배정 → known_hosts 정리 필요 |
| `bad permissions` | 새 pem 파일에 `chmod 400` 누락 |
| `pull access denied` | 새 서버에서 `docker login` 미실행 |
| `no configuration file provided` | 새 서버에 compose 파일 미전송 |

**배운 것**: 인스턴스를 지우고 만들 때마다 같은 세팅을 반복하게 됩니다. 그래서 "서버 초기 세팅 체크리스트"를 README에 문서화했고, Elastic IP로 주소를 고정했으며, Docker Hub 로그인은 워크플로가 자동으로 처리하도록 옮겼습니다. **반복되는 수동 작업은 자동화하거나 문서화한다** — 이번 프로젝트에서 가장 실감했습니다.

## CI/CD를 붙이며

`.yml` 작성법을 몰라 강사님 코드를 보고 작성한 뒤, AI에게 주석을 붙여 설명해달라고 해서 이해했습니다. 정리하면 문법의 핵심은 다섯 가지였습니다.

1. **들여쓰기가 구조** — 파이썬처럼 계층을 만듭니다. 스페이스 2칸이 관례고 탭은 에러입니다. yml 에러의 대부분이 여기서 납니다.
2. **`키: 값`과 리스트 `- 항목`** — 이 두 가지가 문법의 거의 전부입니다.
3. **계층 구조** — `jobs`(VM 단위, 병렬) > `steps`(순차 실행) > `uses`(액션 재사용) 또는 `run`(명령 직접 실행).
4. **`${{ }}`는 변수 치환** — `secrets.`(비밀값), `github.`(내장 정보), `steps.<id>.outputs.`(이전 단계 결과).
5. **흐름 제어** — `needs:`로 순서를 강제하고 `if:`로 조건을 걸어, "test 통과 → main일 때만 build → build 성공 시 deploy" 파이프라인을 구성합니다.

한 가지 흥미로웠던 점은 히어독(`<< 'EOF'`) 안의 `${{ secrets.SERVER_USER }}`가 동작하는 이유였습니다. **셸 변수(`$USER`)와 Actions 변수(`${{ }}`)가 치환되는 시점이 다르기** 때문에, Actions가 ssh 실행 전에 먼저 값을 바꿔 넣어줍니다. 이걸 이해하고 나서야 워크플로 파일을 "읽을 수 있다"는 느낌이 들었습니다.

## 서비스 품질에 대한 아쉬움

배포에 시간을 많이 쓴 탓에 **답변 품질 개선은 손을 대지 못했습니다.** 실제 응답을 확인해보면 문제가 명확합니다.

같은 질문("삼성전자 주식 뉴스 알려줘")에 매번 다른 답이 나오고, 검색된 뉴스에 없는 내용("고도화", "실적 추정치 하향", "KDC 택배 계약")이 등장합니다. 원문을 복사한 게 아니라 모델이 재구성한 것이라 **요약은 하고 있지만 정확도가 낮은** 상태입니다.

원인을 두 층으로 나눠 봤습니다.

**검색 품질 (더 큰 원인)**

- 질문을 그대로 검색 쿼리로 사용 → 종목과 무관한 중국 증시 기사가 걸림
- `contexts`에 뉴스가 1건만 들어옴 → 모델이 고를 재료가 부족
- 유사도가 낮은 문서도 그대로 통과 → 관련 없는 뉴스로 답을 생성

**생성 모델의 한계**

- 소형 모델이라 재료가 좋아도 문법이 깨지거나 지어내는 경향
- temperature가 높아 같은 질문에 답이 매번 달라짐

RAG는 "검색이 8할"이라는 말이 있을 정도라, 모델을 다시 학습하기보다 **검색 개선이 가성비가 훨씬 좋다**는 판단입니다. 다음 우선순위는 이렇게 잡았습니다.

1. 종목명 추출 후 검색 쿼리 구성
2. `top_k`를 3~5로 확대
3. 관련도 임계값을 두고, 미달이면 "관련 뉴스를 찾지 못했습니다"로 폴백 — 없는 답을 지어내는 것보다 낫다
4. temperature를 낮춰 생성 안정화

## 정리

이번 프로젝트에서 **모델을 만드는 일과 서비스를 운영하는 일은 다른 종류의 문제**라는 걸 체감했습니다. 학습 코드가 잘 돌아가는 것과, 그 모델이 다른 사람이 접속할 수 있는 서버에서 안정적으로 돌아가는 것 사이에는 생각보다 많은 단계가 있었습니다.

특히 배포 과정에서 겪은 실패들은 대부분 **"어디에 무엇이 있는지"에 대한 오해**에서 나왔습니다. 모델 파일이 git에 있는지, 이미지에 있는지, 서버 디스크에 있는지, 컨테이너 안에 있는지 — 이 경계를 정확히 알고 나서야 문제가 풀렸습니다.

다음에는 배포 구조를 먼저 잡고 모델을 얹는 순서로 진행하면 훨씬 수월할 것 같습니다. 그리고 남은 시간은 품질 개선과 nginx를 활용하여 80포트로 열고, 제미나이 부분을 공개가중치 모델로 변경할 것 입니다.
